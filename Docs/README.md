# Ays 文档组织与命名规范

## 1. 目录组织

每个独立需求使用一个需求目录，目录名由稳定需求编号和英文短名组成：

```text
Docs/
├── README.md
├── REQ-001-character-locomotion-state-refactor/
│   ├── index.md
│   ├── design-v1.0.md
│   └── implementation-v1.0.md
└── ...
```

根目录文档可以暂时保留作为历史基线或跨需求参考；新需求必须使用独立目录。

## 2. 命名规则

### 2.1 需求目录

格式：`REQ-<三位编号>-<lowercase-kebab-case>`

- 编号在项目内唯一且不复用，例如 `REQ-001`。
- 短名使用英文小写和连字符，避免缩写堆叠。
- 需求编号描述“要解决的问题”，不要使用实现类名作为目录名。

### 2.2 需求索引

固定命名为 `index.md`，只承担三项职责：

1. 简述需求背景、目标和当前状态。
2. 列出设计、实施、决策和验证文档的链接。
3. 记录负责人、更新时间或待决策事项（如果项目需要）。

### 2.3 设计文档

格式：`design-v<主版本>.<次版本>.md`，例如 `design-v1.0.md`。

- 主版本变化表示架构方向或核心边界发生变化。
- 次版本变化表示兼容方向的补充、澄清或小幅调整。
- 已发布版本不覆盖；新版本复制后修改并在索引中标注当前版本。

### 2.4 实施文档

格式：`implementation-v<主版本>.<次版本>.md`，例如 `implementation-v1.0.md`。

实施文档记录执行顺序、代码映射、任务拆分、验收标准、回滚点和测试结果。实现过程中如果实施策略发生实质变化，应创建新版本，不要覆盖已开始执行的版本。

当一个需求需要按阶段分别执行时，阶段文档使用：`implementation-phase-<阶段号>-v<主版本>.<次版本>.md`，例如 `implementation-phase-0-v1.0.md`。需求目录的 `index.md` 应同时链接总实施方案和当前阶段文档。

### 2.5 可选文档

- `decision-<topic>-YYYYMMDD.md`：记录单个架构决策或取舍。
- `test-report-v<主版本>.<次版本>.md`：记录专项验证结果。
- `notes-<topic>.md`：仅用于未定稿的调研笔记，不作为正式设计依据。

## 3. 版本与状态

文档首部建议包含：

```text
状态：草案 / 提案 / 实施中 / 已完成 / 废弃
版本：v1.0
更新时间：YYYY-MM-DD
```

`index.md` 必须明确当前生效的设计版本和实施版本。旧版本保留历史记录，但不应被新代码或新任务引用。

## 4. 链接约定

- 同一需求目录内使用相对链接，例如 `[设计文档](design-v1.0.md)`。
- 跨需求引用使用从当前文件出发的相对路径。
- 源码、资产和外部资料使用反引号或 Markdown 链接，路径必须能在项目中定位。
- 重命名文档时同步更新所属 `index.md` 和其它正式文档中的链接。
